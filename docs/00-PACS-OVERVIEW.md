# PACS 总览

版本：0.1.0｜状态：Foundation

## 1. 为什么建立 PACS

需要迁移的不是某个模型的提示词，而是长期协作中形成的工作能力：理解需求、获取上下文、建立问题模型、拆解任务、选择工具、控制执行、核验证据、保存状态，并把有效经验沉淀为可复用资产。

模型和平台会变化；只要能力接口和治理原则稳定，资产就能迁移。

## 2. 定义

PACS 是模型无关的个人 AI 能力系统，包含治理层、接口层、原子能力层、工作流层、平台适配层、执行层和人类控制层。

## 3. 概念区分

| 概念 | 定义 | 不应混淆为 |
|---|---|---|
| Capability | 可重复完成的一类职责 | 一段提示词 |
| Skill | 能力的可执行封装，含触发、输入、步骤、输出和验收 | Agent 本身 |
| Workflow | 多个能力的有序组合 | 单体超长 Skill |
| Agent | 执行任务的智能主体 | 能力规范 |
| Harness | 提供上下文、工具、权限、运行循环和状态的环境 | 模型 |
| Adapter | 将公共能力映射到平台机制 | 核心能力 |
| Tool | 执行具体操作的外部能力 | 自主决策者 |
| Constitution | 约束所有能力和执行主体的治理原则 | 平台提示词 |

## 4. 个人协作画像摘要

用户倾向将 AI 用于真实项目和交付，而非仅用于问答；先理解背景与系统关系，再施工；要求事实、推断、假设分离；重视版本、状态、测试、回滚、验收和交接；偏好模块化、可复用和受控执行；不追求无意义的自动化数量。详见 docs/03-USER-PROFILE.md。

## 5. 默认任务生命周期

INTAKE → CONTEXT → MODEL → PLAN → ROUTE → EXECUTE → VERIFY → PERSIST

简单问题可走最短路径；高风险、长周期、多工具任务应完整执行。

## 6. 适用场景

软件工程、行业研究、教育教学、内容生产、商业探索和个人输出。

## 7. 设计原则

1. 核心资产可读、可移植、可组合。
2. Skill 单一职责；复杂任务由 Workflow 组合。
3. Adapter 处理平台差异，不复制核心原则。
4. 工具调用受权限和风险等级约束。
5. 结果包含证据、限制和未解决事项。
6. 项目状态持久化，不依赖聊天上下文。
7. 以真实任务验证，不以文档数量或自动化程度衡量成熟度。

## 8. 不作出的承诺

PACS 不保证所有平台具有相同工具、记忆、Skills、MCP 或自动化能力；不保证不同 Harness 中表现完全一致；不替代专业审查；不允许 AI 因为“能操作”就自行执行高风险操作。
