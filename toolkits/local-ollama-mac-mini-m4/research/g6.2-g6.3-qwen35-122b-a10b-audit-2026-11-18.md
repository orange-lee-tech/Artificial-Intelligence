## 2. Exact weight accounting

TurboQuant-MLX's `turboquant-plan` is explicitly header-only: it reads safetensors headers and config without materializing tensors. Its footprint calculation sums tensor bytes from dtype × shape and separates tensors matching the streamed-expert naming rule from the resident remainder.

For the pinned 122B checkpoint, the published planner output is:

| Component | Exact reported size |
|---|---:|
| Total weights | 54.1 GB |
| Streamable routed experts | 50.2 GB |
| Resident / non-expert remainder | 3.9 GB |
| KV projection | 24.0 KB/token |

These three weight numbers are internally consistent at one-decimal GB precision: 50.2 + 3.9 = 54.1 GB.

Approximate binary equivalents:

- total: ~50.38 GiB;
- routed experts: ~46.75 GiB;
- resident remainder: ~3.63 GiB.

**Evidence boundary:** 50.2 GB and 3.9 GB are exact according to the TurboQuant header planner for this checkpoint. PACS has not independently downloaded or parsed the 11 shard headers, so this report does not claim an independent byte-for-byte reproduction.

## 3. Non-expert shell

The resident 3.9 GB is the checkpoint's non-streamed weight remainder. It includes the always-resident model components rather than the 50.2 GB routed expert pool.

This is not the full inference peak.

Runtime memory additionally includes:

- expert cache;
- KV/recurrent state;
- MLX runtime/buffer overhead;
- prefill scratch;
- allocator/cache effects.

TurboQuant-MLX's current memory model uses approximately 1.1 GB runtime overhead above resident weights for its projected peak, based on its calibrated 16 GB mini measurements.

Thus the short-context baseline is approximately:

`3.9 GB resident + 1.1 GB runtime = 5.0 GB`

before the expert cache and meaningful KV growth.

## 4. Expert pool / cache floor

The model has 48 MoE layers and native top-k 8.

A shape-uniform back-of-envelope derived from the published 50.2 GB expert total implies an average expert bundle of roughly 3.9 MiB. This is **not** used as an exact per-layer figure because PACS has not parsed the shard headers.

The runtime therefore must not assume:

`cache-budget = exact peak pool`

The actual streaming runtime allocates cache slots and must satisfy the per-layer top-k requirement.

The published 4 GB cache result is well above any plausible native top-k floor for this checkpoint, so the initial question is not whether 2/3/4 GB can hold one routed step; it is how much cache reduces repeated SSD reads without consuming too much Metal working-set headroom.

## 5. 16 GiB theoretical memory envelope

The model author's 16 GB M4 mini measurements report:

- 1 GB cache -> ~6.0 GB MLX peak;
- 4 GB cache -> ~9.0 GB MLX peak;
- the relationship is approximately `5 GB + cache budget`;
- Metal working-set cap is reported at approximately 10.5 GB.

Using that measured relationship, the requested cache sweep is:

| Expert cache | Projected MLX peak, short context | Headroom vs 10.5 GB working-set cap |
|---:|---:|---:|
| 2 GB | ~7 GB | ~3.5 GB |
| 3 GB | ~8 GB | ~2.5 GB |
| 4 GB | ~9 GB | ~1.5 GB |

These are **projections**, not PACS measurements.

### KV growth

The model's hybrid attention geometry gives a projected FP16 KV cost of 24.0 KB/token.

Approximate incremental KV:

| Context | KV |
|---:|---:|
| 8K | ~0.19 GiB |
| 16K | ~0.38 GiB |
| 32K | ~0.75 GiB |
| 64K | ~1.50 GiB |

Therefore the 4 GB cache configuration is not a universal 16 GiB configuration:

- 8K: ~9.2 GB projected;
- 16K: ~9.4 GB projected;
- 32K: ~9.7 GB projected;
- 64K: ~10.5 GB projected.

At 64K, 4 GB cache effectively consumes the whole reported Metal working-set envelope before additional uncertainty. This is not acceptable as an initial unattended configuration.

**Initial PACS smoke-test target:** 3 GB expert cache, short context (<=8K), batch 1, one request.

A later 4 GB A/B run is permitted only after the 3 GB run is stable.

## 6. TS900 I/O comparison

PACS's corrected TS900 baseline is:

- sequential cache-bypass read: 834.7 MiB/s;
- QD1 4 KiB read: 5,492.1 IOPS;
- QD1 64 KiB read: 2,983.6 IOPS.

The sequential number is the only useful first-order bulk-streaming comparison; the random results do not represent the runtime's coalesced expert access pattern.

The 122B author's 16 GB M4 mini result at 4 GB cache reports:

- expert hit-rate: 44.6%;
- disk read: ~0.93 GB/token;
- decode: ~1.1 tok/s.

That observed 1.1 tok/s and 0.93 GB/token imply an effective disk payload rate of roughly:

`0.93 GB/token × 1.1 token/s ≈ 1.02 GB/s`

This is an inference about the author's measured run, not a published SSD specification.

The TS900's 834.7 MiB/s equals approximately 0.875 GB/s decimal.

If the same 0.93 GB/token traffic pattern were maintained and the TS900 were the sole bottleneck, the theoretical I/O floor would be:

`0.93 GB / 0.875 GB/s ≈ 1.06 s/token`

or approximately:

`0.94 tok/s`

before compute, synchronization, prefetch misses, filesystem overhead, or contention.

Therefore the published 1.1 tok/s result should **not** be used as the expected TS900 result. A first-order expectation is below ~0.94 tok/s at the same traffic pattern.

For the author's 1 GB cache result:

- disk read ~1.78 GB/token;
- 0% hit rate;
- TS900 I/O-only ceiling at that traffic is ~0.49 tok/s.

The 4 GB cache therefore has a strong I/O argument on this particular external SSD: the published traffic falls from 1.78 to 0.93 GB/token, a ~47.8% reduction. However, 2 GB and 3 GB cache traffic cannot be inferred reliably from the published endpoints and must be measured.

## 7. External SSD vs author's environment

The author's hardware is described as a base M4 Mac mini 16 GB and the result is explicitly disk-bandwidth-bound.

The storage device used by the author is not identified sufficiently to treat its I/O path as equivalent to PACS's TS900.

Therefore:

- model architecture compatibility transfers reasonably well;
- memory geometry transfers only as a source-level reference;
- exact tokens/s does not transfer;
- exact expert-cache hit rate does not transfer;
- exact disk-read rate may change with filesystem, SSD, USB path, queueing and cache behavior.

PACS should treat 834.7 MiB/s as a conservative first-order storage ceiling until a runtime-level read trace is measured.

## 8. Runtime compatibility

TurboQuant-MLX currently supports the `qwen3_5_moe` family and expert streaming.

The current runtime source:

- reads safetensors metadata without materializing all experts;
- keeps non-expert weights resident;
- pages routed experts from disk;
- uses LRU expert caching;
- supports parallel prefetch;
- supports explicit cache budgets;
- has optional memory/wired-memory controls.

Important for this project:

1. `wire_memory` must remain OFF for the first test.
2. MTP/draft must remain OFF.
3. Fan-out must remain OFF initially because the runtime documentation explicitly warns that it can lose on bandwidth-bound external storage.
4. `F_NOCACHE`/page-cache behavior must be observed on our macOS 26.2 host rather than assumed from source.
5. Batch size must remain 1.
6. No concurrent local model request is allowed.
